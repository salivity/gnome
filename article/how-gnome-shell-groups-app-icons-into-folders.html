How GNOME Shell Groups App Icons into Folders

GNOME Shell provides an intuitive, clutter-free application grid that allows users to organize software into custom app folders. This article explains the mechanisms behind this functionality, detailing how GNOME handles drag-and-drop folder creation, manages folder metadata through the GSettings configuration system, dynamically matches applications using desktop entries, and renders these groups within the Shell interface.

The Drag-and-Drop Interaction Layer

At the user interface level, folder creation relies on clutter-based drag-and-drop interactions handled by GNOME Shell's JavaScript frontend (specifically within appDisplay.js). When a user drags one application icon and drops it directly onto another within the application grid, GNOME Shell recognizes the collision event.

Instead of reordering the icons, the shell triggers a folder-creation routine. It groups the two .desktop application identifiers together, creates a folder wrapper element, and replaces the individual launcher icons with a single folder preview containing smaller representations of the grouped apps. Users can remove applications by dragging them out of the folder view back to the main grid, which automatically dissolves the folder once only a single application remains.

Configuration Storage via GSettings and dconf

GNOME Shell does not move physical files or alter system directories to create application folders. Instead, it stores folder structure and hierarchy as metadata in the dconf configuration database under the GSettings schema:

org.gnome.desktop.app-folders

Within this schema, the key folder-children holds an array of string identifiers (such as ['Utilities', 'Sundry', 'CustomFolder1']). Each ID corresponds to a relocatable GSettings path:

org.gnome.desktop.app-folders.folder:/org/gnome/desktop/app-folders/folders/<folder-id>/

Inside each relocatable folder schema, GNOME Shell manages four primary keys:

  • name: A string specifying the display name of the folder.
  • translate: A boolean determining whether GNOME should attempt to translate the folder name based on system locale files.
  • apps: An array of explicit desktop file names (e.g., ['org.gnome.Calculator.desktop', 'org.gnome.Characters.desktop']) designated for that folder.
  • categories: An array of standard Freedesktop.org menu categories (such as ['Utility', 'Development']) that automatically pull matching applications into the folder.
  • excluded-apps: An array of .desktop IDs specifically prevented from being populated via the categories rule.

Automatic and Dynamic Folder Population

GNOME Shell balances manual customization with automated categorization. When generating the application grid, the shell enumerates all valid .desktop files located in the standard XDG data directories (/usr/share/applications and ~/.local/share/applications).

For each application, the shell evaluates whether its identifier appears explicitly in a folder's apps list. If it does not, GNOME Shell checks the Categories field inside the application's .desktop file against the categories array in defined app folders. If a category match is found and the application is not explicitly listed under excluded-apps, GNOME Shell dynamically inserts the application into that folder.

Real-Time Grid Rendering

Because folder states are managed as GSettings keys, GNOME Shell listens for change events on the org.gnome.desktop.app-folders path. Whenever a user creates a folder, edits a folder name, or alters folder contents using the graphical shell, the GNOME Software center, or command-line utilities like gsettings, the backend configuration updates instantly.

Upon detecting these changes, GNOME Shell dynamically redraws the application view without requiring a shell reload or session restart, seamlessly updating icon positions, folders, and page counts in the overview grid.
