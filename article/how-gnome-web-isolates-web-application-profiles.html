How GNOME Web Isolates Web Application Profiles

GNOME Web, also known as Epiphany, allows users to transform websites into standalone desktop applications with independent security boundaries. This article explores the core technical features—including dedicated directory structures, WebKitGTK multi-process architecture, Bubblewrap sandboxing, and desktop portal integration—that enable GNOME Web to deliver strictly isolated sandboxing profiles for individual web applications.

Independent Profile Directories

When a user creates a web application in GNOME Web via the "Install Site as Web Application" feature, the browser generates an isolated profile directory entirely separate from the standard browser instance. Stored in a distinct user data path (typically under ~/.local/share/org.gnome.Epiphany.WebApp-* or within the application's specific Flatpak data directory), each application maintains its own:

  • Cookies and Session Storage: Prevents tracking across apps and between the app and the standard browser.
  • Cache and IndexedDB Data: Ensures offline assets and local databases cannot be read or modified by other web instances.
  • Extensions and Settings: Disables global browser extensions by default, minimizing the attack surface and avoiding script injection risks.

Because these directories are isolated at the filesystem level, web applications run without shared memory, state, or session leakage.

WebKitGTK Multi-Process Architecture

GNOME Web is built on the WebKitGTK engine, which inherently isolates different browsing components into individual system processes:

  • UI Process: Manages the window, system integration, and application shell.
  • Network Process: Handles all network requests, TLS negotiation, and socket communication independently for that specific profile.
  • Web Processes: Renders the DOM, parses CSS, and executes JavaScript. Each origin or instance runs inside its own restricted process.

By splitting these tasks, an exploit or crash within a web application's rendering engine cannot easily compromise the underlying system or access the main browser's runtime memory.

Flatpak and Bubblewrap Sandboxing

When GNOME Web is deployed as a Flatpak, its sandboxing capabilities are significantly enhanced through Bubblewrap. Bubblewrap uses Linux kernel namespaces (mount, network, IPC, PID, and user namespaces) to lock down the execution environment:

  • Filesystem Restrictions: Web apps are blocked from viewing arbitrary host files. They only have access to their specific sandboxed data directory.
  • Process Isolation: An application cannot inspect or manipulate processes running on the host or inside other sandboxes.
  • Device Node Filtering: Direct access to host hardware devices is restricted, preventing unauthorized low-level hardware communication.

Dedicated Application Mode Execution

Each installed web application is launched with a specialized command-line flag (epiphany --application-mode). This flag forces the binary to run as an independent application instance identified by a unique desktop file. It bypasses the standard single-instance D-Bus service used by the main browser window, ensuring that the web app spawns with its own process group and security context rather than attaching to an existing, elevated browser session.

Permission Control via XDG Desktop Portals

GNOME Web relies on XDG Desktop Portals to broker access to system resources. Instead of granting blanket permissions, capabilities such as:

  • File selection (Open/Save dialogs)
  • Camera and microphone access
  • Location services
  • System notifications

are handled through out-of-process system dialogs. The sandboxed web application never gets direct hardware or filesystem access; it receives only the specific resource or data stream approved by the user, enforced strictly on a per-application basis.
