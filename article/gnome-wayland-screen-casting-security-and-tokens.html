GNOME Wayland Screen Casting Security and Tokens

Under the Wayland display protocol, direct screen capturing is blocked by design to prevent unauthorized applications from snooping on the desktop. GNOME solves this by routing screen capture requests through an isolated pipeline consisting of D-Bus portals, PipeWire multimedia routing, and Mutter compositor interfaces. A central component of this mechanism is the screen casting "restore token," a credential that enables applications to resume authorized capture sessions without repeatedly prompting the user, while preserving the sandboxing and security guarantees of the Wayland architecture.

The Wayland Security Model and the Need for Portals

In traditional X11 environments, any client application can read the entire screen buffer and monitor global keystrokes. Wayland eliminates this design flaw by isolating clients from one another; a Wayland client only has access to its own surfaces and cannot inspect the compositor's global output or other running applications.

Because applications cannot capture pixels directly, GNOME relies on the xdg-desktop-portal system. When an application needs to record the screen or share a window, it communicates via D-Bus with xdg-desktop-portal, which in turn invokes the GNOME backend implementation, xdg-desktop-portal-gnome. This backend triggers Mutter (GNOME's Wayland compositor) to prompt the user for permission.

How Screen Casting Tokens Work

Repeatedly asking users to select a display or window every time an application starts degrades usability. To solve this, GNOME implements persistent permission handles known as restore tokens within the ScreenCast portal interface.

  1. Initial Request and Consent: When an application requests screen casting via org.freedesktop.portal.ScreenCast, GNOME displays an explicit system dialogue. The user selects the exact source—such as a specific monitor or individual application window—and confirms permission.
  2. Token Generation: Upon user approval, Mutter assigns a session identifier and generates an opaque, cryptographically random string known as a restore token.
  3. Session Linking: The token maps the approved source (e.g., Output 1 or Window X) to the unique application identity making the request.
  4. Token Storage and Handoff: The portal passes this restore token back to the requesting client application. Trusted clients can store this token locally for future sessions.
  5. Subsequent Sessions: During future launches, the application provides the restore token in its initial D-Bus method call. If the token is valid, GNOME restores the previously granted capture session without triggering a new user prompt.

Preventing Security Exploits and Token Hijacking

GNOME and the portal infrastructure enforce several boundaries to ensure these tokens cannot be abused by malicious software:

  • Application Identity Verification: Tokens are strictly tied to the calling application's identity. For sandboxed applications (such as Flatpak), the portal validates the unique application ID through the sandbox proxy. A rogue application cannot reuse a token generated for an authorized application because the backend detects the mismatched identity.
  • Compositor Authority: The client application never receives raw access to the display server or window handles. The token merely instructs Mutter to open a restricted PipeWire stream. Mutter negotiates file descriptors directly with the PipeWire daemon, ensuring the application receives only the authorized video feed.
  • Token Invalidation: Restore tokens are not perpetual absolute rights. If a user modifies display configurations (such as unplugging a monitor) or closes the target window, the token becomes invalid. GNOME also invalidates tokens if an application requests access parameters that exceed the original authorization.
  • Persistent Visual Indicators: Even when a restore token bypasses the user confirmation dialogue, GNOME displays a global recording indicator in the top panel as long as the capture pipeline is active. This ensures no background process can capture the screen invisibly, regardless of its permission state.
