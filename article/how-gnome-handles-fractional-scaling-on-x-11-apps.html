How GNOME Handles Fractional Scaling on X11 Apps

Fractional scaling on modern high-DPI displays offers a balanced interface size, but running legacy X11 applications within GNOME’s Wayland session introduces visual artifacts and blurriness. Because the legacy X11 architecture lacks native concepts of per-monitor or non-integer scaling, GNOME relies on a combination of compositor-level upscaling, Xwayland emulation, and display filtering to display these clients. This article explains the technical mechanisms GNOME’s Mutter window manager uses to handle fractional scaling for older X11 applications, the root causes of the resulting artifacts, and how modern display protocols manage this limitation.

The Architectural Disconnect Between X11 and Wayland

Modern Wayland architectures handle fractional scaling via dedicated protocols (such as wp-fractional-scale-v1), allowing the compositor to negotiate precise surface dimensions directly with clients. In contrast, the decades-old X11 protocol inherently assumes that display coordinates directly map to physical hardware pixels across a global, uniform coordinate space.

When running an X11 application under GNOME, the app does not communicate directly with Wayland. Instead, it interacts with Xwayland, an X11 server running as a Wayland client. Because standard X11 clients cannot request fractional scaling factors like 125% or 150%, GNOME must mediate the scale discrepancy using the Mutter compositor.

Integer Rendering and Compositor Upscaling

To prevent legacy software from breaking or miscalculating input coordinates, GNOME generally instructs X11 applications to render at a standard scale factor of 100% (1x).

Once the application renders its buffer at standard resolution, GNOME's compositor takes over:

  1. Buffer Interception: Mutter captures the rendered pixel buffer from Xwayland at its native 1x resolution.
  2. Viewport Scaling: The compositor applies a transformation to stretch the surface to match the configured fractional scale of the target display (for example, scaling a 1x surface up by 1.5x on a 150% scaled display).
  3. Filtering: Mutter applies texture filtering (typically bilinear filtering) to smooth out the enlarged pixels.

While this approach prevents the application from rendering tiny, unusable UI elements on high-density screens, it introduces noticeable blurriness. Because non-integer multiples do not map evenly onto physical subpixels, fine details such as font glyphs and line borders lose sharpness.

The Alternative: Integer Oversampling and Downscaling

In some configurations and experimental branches, Mutter has utilized a "scale-up, scale-down" rendering pipeline to handle fractional coordinates:

  • Rendering at 2x: The application is told to scale to the nearest higher integer factor (typically 200%).
  • Downsampling: The compositor downscales the high-resolution buffer to the fractional target (e.g., downscaling a 200% render to 150% target display space).

This technique sharpens text and vector icons significantly compared to stretching a 1x buffer. However, downscaling introduces its own visual artifacts, such as moiré patterns, shimmering during window movement, and uneven line thickness. It also incurs a notable performance penalty, as legacy applications are forced to render substantially more pixels than necessary, increasing memory bandwidth and GPU load.

Input Coordinate Mapping

Artifacts are not exclusively visual; fractional scaling can also cause input inaccuracies. Because the X11 application believes its window exists in a standard 1x coordinate space, Mutter must transform input events on the fly:

  • Mouse Events: Wayland pointer coordinates are converted into the scaled coordinate space before being passed through Xwayland to the client.
  • Window Dimensions: Mutter maps window geometry requests back and forth, preventing cursor drift or missed click targets around small UI elements like close buttons and dropdown menus.

Without this coordinate translation, clicks would register offset from their visually scaled locations.

Moving Beyond Xwayland Scaling

GNOME treats compositor-side scaling of X11 applications as an unavoidable compatibility compromise. The long-term resolution for fractional scaling artifacts does not lie within X11 fixes, but in transitioning applications off the legacy protocol entirely.

When applications are updated to run natively on Wayland using modern toolkits (such as GTK 4 or Qt 6), they bypass Xwayland entirely. In these native environments, GNOME can instruct the application to render directly at the fractional scale factor using Wayland fractional scaling protocols, eliminating scaling artifacts and delivering crisp text and UI elements.
