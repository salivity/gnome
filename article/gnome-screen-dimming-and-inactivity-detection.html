GNOME Screen Dimming and Inactivity Detection

GNOME manages screen dimming through a coordinated subsystem of session monitors, power management daemons, and display compositor interfaces that track user idle time. When input devices cease reporting activity, GNOME calculates inactivity thresholds and gradually reduces screen brightness as an intermediate power-saving step before initiating screen blanking or system suspend. This system ensures energy efficiency while providing immediate visual feedback that allows users to interrupt the timeout sequence before the session locks.

The Core Architectural Components

GNOME’s inactivity and dimming architecture relies on three primary components:

  1. Mutter (The Compositor): Mutter interfaces directly with the display server (Wayland or X11) and input drivers via libinput. It exposes an internal tracking interface known as MetaIdleMonitor over D-Bus (org.gnome.Mutter.IdleMonitor), which tracks raw device inputs such as mouse movements, keystrokes, and touch events on a per-device and global level.
  2. GNOME Settings Daemon (gsd-power): The power plugin inside gnome-settings-daemon defines and enforces power management policies. It subscribes to idle alarms provided by Mutter, maintains user configuration preferences, and commands hardware backlights or display servers to adjust brightness.
  3. GSettings Configuration Backend: The user's idle preferences are stored in the GSettings schema under org.gnome.settings-daemon.plugins.power. Key settings include idle-dim (a boolean enabling or disabling dimming) and sleep-inactive-ac-timeout / sleep-inactive-battery-timeout.

How Inactivity Detection Works

Inactivity tracking operates via event-driven alarms rather than continuous polling:

  • Idle Alarms: Instead of constantly checking the system uptime or input state, gsd-power registers specific idle timers with Mutter’s IdleMonitor. For example, if screen blanking is scheduled for five minutes, gsd-power requests an alarm at a predefined fraction of that duration.
  • Dimming Threshold Calculation: By default, GNOME calculates the screen dimming point proportionally based on the configured screen-off delay. If the idle turn-off delay is set to a short duration, dimming occurs shortly before the screen blanks. If screen-off is disabled entirely, dimming is typically calculated from a static fallback threshold.
  • Input Interruption: When any hardware input event occurs, Mutter resets the idle timer to zero, invalidates active idle alarms, and emits an event indicating activity. gsd-power receives this signal and instantly restores the display to its target operational brightness.

The Dimming Execution Sequence

Once an idle alarm fires, GNOME executes the dimming transition through the following pipeline:

  1. Threshold Reached: Mutter alerts gsd-power that the inactivity threshold for dimming has passed without any registered input events.
  2. Inhibitor Check: gsd-power verifies that no active application has placed an idle inhibitor on the session. Applications playing full-screen video, conducting video calls, or presenting slides request inhibitors via the org.freedesktop.ScreenSaver or org.gnome.SessionManager D-Bus interfaces. If an inhibitor is active, the dimming routine aborts.
  3. Smooth Brightness Reduction: If unobstructed, gsd-power initiates a smooth linear transition downward to a predefined minimum brightness level (usually around 30% of standard brightness, depending on hardware limits). It does this by modifying the display's hardware backlight controllers via the Linux kernel's sysfs interface (/sys/class/backlight) or via D-Bus backlight proxy interfaces.
  4. Transition to Blanking: If the user fails to provide input while the display is dimmed, the idle monitor reaches the final timeout limit, prompting Mutter to power down display outputs via Display Power Management Signaling (DPMS).
