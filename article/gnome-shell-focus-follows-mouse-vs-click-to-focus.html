GNOME Shell: Focus-Follows-Mouse vs Click-to-Focus

GNOME Shell manages window focus through its underlying compositing window manager, Mutter, allowing users to choose between the traditional "click-to-focus" model and cursor-driven "focus-follows-mouse" policies. While the desktop environment defaults to requiring explicit clicks to activate windows, Mutter includes native configuration keys that enable immediate window activation based on pointer position. This article explains how Mutter implements these focus modes, how focus is decoupled from window raising, and how to configure these policies in GNOME.

The Underlying Window Manager: Mutter

GNOME Shell does not handle window tracking directly; it delegates this responsibility to Mutter. Mutter implements X11 and Wayland window management protocols and maintains the internal state of which window holds keyboard and input focus. Mutter exposes its focus configurations through the org.gnome.desktop.wm.preferences GSettings schema.

Focus Modes in GNOME Shell

GNOME Shell provides three primary focus policies defined under the focus-mode key:

  1. Click (Default): A window only gains focus when the user clicks inside its frame or content area. Moving the mouse cursor over unfocused windows produces no change in focus. This mode prevents unintended focus shifts during erratic mouse movement and is standard across most modern desktop environments.
  2. Sloppy: A hybrid focus-follows-mouse behavior. Moving the pointer over a window automatically transfers input focus to that window without requiring a click. If the cursor is subsequently moved away from the window into an empty workspace area or desktop background, the previously focused window retains its focus state until the pointer enters a different window.
  3. Mouse: Strict focus-follows-mouse behavior. Focus immediately follows the pointer. Unlike "sloppy" mode, if the pointer moves out of an active window and onto the empty desktop, the window immediately loses focus, leaving no window focused.

Decoupling Focus from Window Raising

A central feature of GNOME Shell's focus-follows-mouse implementation is the separation between window focus (receiving keyboard input) and window raising (bringing the window to the front of the visual stacking order).

By default, switching to sloppy or mouse focus mode does not automatically raise the newly focused window above overlapping windows. This allows users to read from a top window while typing into a partially occluded window beneath it.

For users who prefer windows to visually surface upon hover, GNOME provides the auto-raise setting:

  • auto-raise (Boolean): When set to true, hovering over an obscured window will automatically bring it to the front.
  • auto-raise-delay (Integer): Controls the delay (in milliseconds) before the window is raised, preventing windows from rapidly shuffling to the top as the cursor passes across the screen.

How to Configure Focus Policies

Focus behavior can be toggled visually using GNOME Tweaks or programmatically using the gsettings command-line utility.

Using the Terminal (gsettings)

To set the policy to focus-follows-mouse ("sloppy"):

gsettings set org.gnome.desktop.wm.preferences focus-mode 'sloppy'

To enable auto-raise with a 300-millisecond delay:

gsettings set org.gnome.desktop.wm.preferences auto-raise true
gsettings set org.gnome.desktop.wm.preferences auto-raise-delay 300

To revert to the standard click-to-focus behavior:

gsettings set org.gnome.desktop.wm.preferences focus-mode 'click'
gsettings set org.gnome.desktop.wm.preferences auto-raise false

Using GNOME Tweaks

In the GNOME Tweaks application, navigate to the Windows section. Under Window Focus, select either Click to Focus, Sloppy, or Secondary-Click. Enabling "Raise Windows on Focus" enables the auto-raise parameter.

Edge Cases and Special Behavior

GNOME Shell modifies focus behavior during specific interactions:

  • Modal Dialogs: If a window spawns a modal dialog, parent windows yield focus to the child dialog regardless of the pointer position until dismissed.
  • Overview Mode: Entering the Activities Overview suspends active window focus rules. Normal focus restores when returning to the desktop.
  • Wayland vs. X11: Under Wayland, pointer constraints and focus tracking are strictly enforced by the compositor for security reasons, whereas X11 clients may occasionally attempt to seize global input focus via standard X11 protocols.
