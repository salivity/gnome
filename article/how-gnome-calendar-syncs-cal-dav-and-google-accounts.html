How GNOME Calendar Syncs CalDAV and Google Accounts

GNOME Calendar synchronizes events with remote CalDAV servers and Google accounts through a modular architecture powered by GNOME Online Accounts and Evolution Data Server. Rather than implementing network protocols and synchronization algorithms directly within the interface, GNOME Calendar functions as a graphical front end, delegating credential management, network transactions, local caching, and two-way synchronization to dedicated system-level background services.

The Role of GNOME Online Accounts (GOA)

Authentication is handled by GNOME Online Accounts (GOA), a desktop service that stores credentials and access tokens.

  • Google Accounts: GOA uses OAuth 2.0 to authenticate with Google. It manages the token lifecycle, automatically refreshing expired access tokens so the calendar services maintain uninterrupted access.
  • CalDAV Accounts: GOA stores the user's server URL, username, and password securely in the GNOME Keyring.

Once an account is configured in GOA, the service informs the desktop environment that calendar capabilities are available for that provider.

Evolution Data Server (EDS) as the Middleware

Evolution Data Server (EDS) is the central engine responsible for all calendar data management on GNOME. GNOME Calendar interacts with EDS via D-Bus, an inter-process communication mechanism.

EDS contains specialized backends for different calendar providers:

  • A generic CalDAV backend for standard CalDAV services (such as Nextcloud, Fastmail, or self-hosted Radicale instances).
  • A specialized Google backend (or the CalDAV backend pointed to Google's CalDAV endpoint) that attaches the OAuth 2.0 bearer tokens obtained from GOA.

EDS maintains an offline SQLite database containing cached copies of all events, tasks, and calendar metadata. When GNOME Calendar opens, it reads directly from this local cache, ensuring instant loading even without an active internet connection.

The Synchronization Protocol

EDS handles the two-way network synchronization using standard web protocols:

  1. Discovery: EDS sends an HTTP PROPFIND request to the remote CalDAV endpoint to locate user calendar collections and identify supported server capabilities.
  2. Change Detection: To minimize bandwidth, EDS checks collection entity tags (ETags) or uses the WebDAV sync collection report (RFC 6578). This allows EDS to ask the server only for items that have changed since the last known synchronization token.
  3. Fetching Updates: When changes are detected, EDS sends an HTTP REPORT request to download updated event data formatted as standard iCalendar (.ics / RFC 5545) objects. EDS then updates the local SQLite cache and emits a D-Bus signal, prompting GNOME Calendar to redraw the view.
  4. Pushing Changes: When a user creates, edits, or deletes an event in GNOME Calendar:
    • GNOME Calendar passes the change to EDS over D-Bus.
    • EDS immediately updates the local database so the interface reflects the edit without delay.
    • EDS formats the event into an iCalendar payload and sends an HTTP PUT request (for additions and edits) or an HTTP DELETE request to the remote server.

Periodic and Real-Time Refreshes

EDS schedules background refresh timers to periodically query the remote CalDAV or Google servers for remote changes. When network connectivity drops, EDS queues local modifications and pushes them to the remote server once the connection is restored, resolving conflicts based on the latest modification timestamps.
