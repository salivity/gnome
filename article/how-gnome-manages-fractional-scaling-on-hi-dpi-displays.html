How GNOME Manages Fractional Scaling on HiDPI Displays

This article examines the underlying mechanisms used by the GNOME desktop environment to support fractional scaling—such as 125% or 175%—on high-density (HiDPI) displays. It details the architecture of GNOME's compositor, Mutter, the shift from integer-only scaling and viewport downsampling to modern Wayland protocols like wp_fractional_scale_v1, and the strategies used to handle legacy X11 applications via Xwayland.

The Architectural Challenge of Fractional Scaling

Historically, Linux display architectures only supported integer scaling factors (such as 100%, 200%, or 300%). While integer scaling simplifies rendering by multiplying logical pixels by whole numbers, modern displays often feature resolutions where 100% renders text too small and 200% renders UI elements excessively large. Fractional scaling bridges this gap, but requires the rendering pipeline—including the display server, compositor, toolkit, and client applications—to coordinate non-integer coordinate transformations without causing visual artifacts or performance degradation.

Mutter's Oversampling and Downscaling Approach

In GNOME under Wayland, fractional scaling was initially implemented as an experimental feature in Mutter using an oversampling pipeline:

  1. Logical Framebuffer Upscaling: Mutter renders the application surface to an offscreen buffer at the next highest integer scale factor. For instance, if a user selects 150% scaling, Mutter instructs the client application to render at 200% (2x integer scale).
  2. GPU Downscaling: Once the frame is drawn at the higher integer resolution, Mutter uses GPU texture filters (typically bilinear or bicubic filtering) to scale the rendered output down to the target display resolution (1.5x).

This technique ensured that UI elements and vector assets remained sharp and avoided layout bugs in toolkits that only understood integer coordinates. However, it introduced minor drawbacks: increased GPU memory bandwidth, higher power consumption, and slight blurring on raster graphics or subpixel-rendered text due to bilinear filtering.

Native Fractional Scaling via Wayland Protocols

To eliminate the performance and clarity penalties of downscaling, the Wayland ecosystem developed the wp_fractional_scale_v1 protocol extension, which GNOME has integrated into Mutter and GTK.

Instead of relying on integer surface scaling with subsequent post-processing, this protocol establishes a direct negotiation mechanism:

  • Protocol Negotiation: The compositor notifies client surfaces of the exact preferred fractional scale factor (represented as an integer fraction, such as 120/120 for 1.0, or 150/120 for 1.25).
  • Direct Client Rendering: Modern toolkits (such as GTK4 and Qt 6) read this value and render vector elements, glyphs, and UI components directly at the target physical resolution.
  • Buffer Viewport Integration: Paired with the wp_viewporter protocol, clients can attach pixel buffers of any arbitrary physical size to a surface and define its logical size independently. This allows the compositor to present frames with pixel-perfect precision without running a GPU downsampling pass.

Toolkits and Font Scaling Mechanisms

GNOME coordinates scaling across multiple layers of the desktop stack:

  • GTK Integration: GTK4 provides full support for fractional scaling via Cairo and GSK (GTK Scene Kit), rendering graphics at the exact physical pixel boundary. GTK3, which relies on integer grid layouts, depends more heavily on the compositor's downsampling mechanism or text-only scaling adjustments.
  • Text Scaling Factor: As a lightweight alternative or supplementary mechanism, GNOME utilizes the text-scaling-factor setting in GSettings (org.gnome.desktop.interface). This alters the DPI passed to the font-rendering subsystem (FreeType and HarfBuzz) without changing the overall coordinate dimensions of UI controls, leaving window chrome at 100% while enlarging typography.

Handling Legacy Applications with Xwayland

Applications that run through Xwayland present a distinct challenge because the traditional X11 protocol lacks native concepts of per-monitor or fractional scaling. GNOME handles X11 applications through two primary methods:

  1. Compositor Scaling: Mutter can treat the X11 window as a 100% surface and scale it up to the target fractional size. While this preserves proper window sizing, it causes text and UI elements to appear blurry.
  2. Xft.dpi Adjustments: Users or environments can set the Xft.dpi resource via xrdb to scale text inside X11 apps. However, this does not scale non-text UI elements evenly and fails across multi-monitor setups with mismatched display densities.

Through the combination of wp_fractional_scale_v1, modern GPU-accelerated rendering in Mutter, and adaptive toolkit support, GNOME continues to transition away from oversampling techniques toward native, per-surface fractional rendering across all HiDPI setups.
