How GNOME Runs Background Apps Without System Trays

Modern versions of the GNOME desktop environment have eliminated legacy system tray icons in favor of a standardized, secure, and user-centric application lifecycle. Instead of allowing persistent tray icons to arbitrarily manage process lifecycles and clutter the interface, GNOME handles background tasks through a combination of systemd user sessions, XDG Desktop Portals, D-Bus application activation, and a native Quick Settings background apps monitor. This ensures processes can continue running or performing tasks seamlessly without requiring persistent icons pinned to the top bar.

The Problem with Legacy System Tray Icons

Legacy tray icons combined multiple distinct responsibilities into a single tiny icon: task status, notification dispatch, window minimization targets, and process lifecycle management. This design broke user experience consistency, bypassed accessibility tools, and lacked security sandboxing. GNOME separated these responsibilities into distinct, native system services rather than a persistent panel of icons.

Systemd User Session Integration

GNOME deeply integrates with systemd at the user level (systemd --user). When you log in, systemd manages the lifecycle of your graphical session and its associated background services. Background tasks—such as file indexing (tracker-miner-fs), backup utilities, or sync daemons—run as isolated systemd units or slice services. This architectural separation allows the backend process to survive window closures, restarts, or crashes independently of the graphical user interface.

XDG Desktop Portals and Permissions

For containerized applications such as Flatpaks, GNOME utilizes the XDG Desktop Portal system, specifically the org.freedesktop.portal.Background portal. When an application attempts to run after its last window has closed, the background portal intercepts the request:

  • The portal checks if the application has explicit permission to run headlessly.
  • If it does not, the user is prompted to grant or deny background execution rights.
  • Permissions are remembered and can be revoked at any time through GNOME Settings under the Applications tab.

The Quick Settings Background Apps Menu

To preserve user visibility into what is running on their machine, GNOME introduced the "Background Apps" section inside the system status (Quick Settings) menu. When an application continues running with no active windows, it automatically registers in this native list.

Users can click on an entry to bring its interface forward, or click the dedicated close button next to the application name to terminate the process cleanly via standard signals. This gives users full operational visibility without requiring a tray icon for every background task.

D-Bus and App Separation

Applications developed for the modern Linux desktop typically split their architecture into a headless backend daemon and a graphical frontend (GTK client). The communication between both components happens over the D-Bus system or session bus.

When the user closes the window, the GUI frontend exits, freeing graphic resources. The backend daemon remains connected to D-Bus to listen for system events, network triggers, or scheduled jobs. When user interaction is required again, the daemon triggers a desktop notification or asks the desktop to launch the GUI frontend on demand.

Purpose-Built Replacements for Status Interfaces

Features historically crammed into status icons are now routed through standardized desktop APIs:

  • Media Controls: Audio and video applications implement the MPRIS (Media Player Remote Interfacing Specification) D-Bus interface, which displays controls directly inside the notification shade and lock screen.
  • Alerts and Status Updates: Applications emit native desktop notifications with actionable buttons rather than blinking or changing an icon in the corner of the screen.
  • Online Accounts: Synchronization tasks (Google Drive, Nextcloud, Microsoft 365) are handled globally by GNOME Online Accounts and evolution-data-server rather than individual standalone tray daemons.
