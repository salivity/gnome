How GNOME Manages Flatpak Sandboxing Permissions

This article examines how the GNOME desktop environment handles application sandboxing permissions using Flatpak and the underlying XDG permission store architecture. By utilizing Bubblewrap for low-level process isolation, XDG Desktop Portals for dynamic API mediation, and a dedicated permission store backend to track user consents, GNOME enforces a zero-trust security model. Readers will understand how permission requests are intercepted, stored, and managed through native GNOME graphical interfaces.

The Foundation of Flatpak Sandboxing

Flatpak isolates desktop applications using Bubblewrap, a low-level utility that leverages Linux kernel namespaces, cgroups, and seccomp filters. By default, a sandboxed application runs with no network access, an empty /home directory, no access to host devices (like webcams or microphones), and isolated IPC (Inter-Process Communication) mechanisms.

Static permissions, such as baseline network access or specific directory mounts, are declared during application packaging and enforced at launch. However, dynamic access to sensitive resources requires a secure mediation layer to avoid granting broad, permanent system access.

The Bridge: XDG Desktop Portals

Sandboxed applications cannot directly access hardware or host files; instead, they interact with the host through XDG Desktop Portals over D-Bus. When an application requests an action—such as opening a file, taking a picture, or reading the system location—it sends an IPC request to xdg-desktop-portal.

The desktop portal forwards the request to the desktop-specific backend, which in GNOME is xdg-desktop-portal-gnome (formerly handled via xdg-desktop-portal-gtk). This backend draws native GNOME dialogs directly in the user's secure desktop session, outside the sandbox boundary. Because the application cannot forge or click these dialogs programmatically, malicious software cannot grant itself access.

The Flatpak Permission Store

The decisions made through portals are recorded and tracked by the Flatpak Permission Store (xdg-permission-store), a persistent D-Bus service managed by Flatpak.

The permission store functions as follows:

  • Storage Engine: It maintains a database (typically located in ~/.local/share/flatpak/db/) that maps application IDs (e.g., org.gnome.Epiphany) to specific permissions, resources, and access levels (such as "yes", "no", or "ask").
  • Permission Tables: Separate tables exist for various device classes and APIs, including camera, microphone, location, background running, and file access.
  • Lookup Sequence: When an app invokes a portal API:
    1. The portal queries the permission store using the application's unique ID.
    2. If the store contains an explicit grant or denial, the portal acts accordingly without prompting.
    3. If no entry exists, the portal initiates an interactive system prompt.
    4. The user's response is communicated back to the permission store, where it is written permanently for subsequent sessions.

Dynamic File Access via the Document Portal

File access receives specialized handling through the Document Portal (xdg-document-portal), which works in tandem with the permission store. When an application prompts the user to open or save a file via the FileChooser portal, the host presents a native GNOME file picker.

Once the user selects a file, the Document Portal creates a unique FUSE (Filesystem in Userspace) mount point located inside the application's sandbox (usually mounted under /run/user/$UID/doc/). The permission store registers that specific file path to the calling application ID. This mechanism allows the app to read or write only the explicitly selected file without gaining broader access to the user's filesystem.

User Management Through GNOME Settings

GNOME integrates directly with the permission store through its graphical Control Center (gnome-control-center). Under Settings > Privacy and Settings > Apps, GNOME queries the permission store to list all Flatpak applications that have requested access to hardware devices or host services.

Users can toggle permissions (such as microphone, camera, notifications, or automatic background execution) on a per-app basis at any time. When a toggle is switched, GNOME updates the corresponding entry in the Flatpak permission store database via D-Bus, immediately revoking or granting the capability without requiring a rebuild or reinstallation of the application bundle.
