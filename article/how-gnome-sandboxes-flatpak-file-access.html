How GNOME Sandboxes Flatpak File Access

GNOME isolates Flatpak applications from direct filesystem access by combining Linux kernel-level containerization with an external portal-based permission system. Flatpak applications run in restricted environments created via Bubblewrap, which strip them of the ability to see or modify host directories by default. When an application needs to read or write a file, GNOME handles the interaction outside the sandbox using the XDG Desktop Portal system, ensuring that applications only receive access to specific files explicitly chosen by the user.

Bubblewrap and Kernel Namespaces

At the base of the isolation layer is Bubblewrap, an unprivileged sandboxing tool that utilizes core Linux kernel features, primarily namespaces and cgroups. When GNOME launches a Flatpak, Bubblewrap creates a distinct mount namespace for the application.

In this isolated mount namespace:

  • The host’s root filesystem is invisible.
  • A dummy, minimal root filesystem containing only the necessary Flatpak runtime libraries (such as GNOME's runtime) is mounted as read-only.
  • The application is assigned an isolated storage directory (~/.var/app/<app-ID>/) for configuration and cache files.
  • Direct access to the user's home directory (/home/<user>) or root directories (/etc, /usr, /var) is blocked unless explicitly declared in the application's permission manifest.

XDG Desktop Portals

To allow applications to open and save files without granting broad access to the filesystem, GNOME relies on the XDG Desktop Portal framework, specifically the xdg-desktop-portal-gnome backend. Portals act as secure D-Bus bridges between the sandboxed application and the host desktop.

When an application calls a standard "Open File" or "Save File" dialog, it does not render the dialog itself. Instead, the application makes a D-Bus request to the portal. The GNOME desktop intercepts this request and renders an out-of-process GTK file chooser directly on the host. Because the dialog runs outside the sandbox, the user can browse their entire filesystem safely; the sandboxed application cannot observe where the user navigates or what files exist in the chosen directories.

The Document Portal and File Descriptors

Once the user selects a file and clicks "Open" in the GNOME file dialog, access is granted through one of two mechanisms:

  1. File Descriptors: For straightforward read or write tasks, the portal can open the file on the host side and pass an open file descriptor over D-Bus back into the sandboxed application. This gives the app access to the stream of that single file without exposing its path or parent directory.
  2. The Document Portal (FUSE): For applications that require path-based access, GNOME utilizes a user-space virtual filesystem (FUSE) located at /run/user/<uid>/doc/. The portal creates an isolated, virtual mount path for the specific file inside the sandbox. The application can read or modify the file through this mount, while the underlying host location remains concealed.

Through the integration of Bubblewrap isolation, out-of-process GNOME portals, and fine-grained file-descriptor delegation, GNOME prevents Flatpak applications from reading arbitrary files while maintaining standard desktop functionality.
