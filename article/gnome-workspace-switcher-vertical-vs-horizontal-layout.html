GNOME Workspace Switcher: Vertical vs Horizontal Layout

GNOME Shell renders its workspace switchers by managing a scene graph of visual actors powered by Mutter and Clutter, adapting transformation matrices, scrolling coordinates, and layout allocations to fit either a vertical or horizontal axis. While GNOME 40 shifted the default paradigm to a horizontal spatial model to align with trackpad gesture physics, vertical layouts—used in earlier versions and maintained via community extensions—rely on distinct layout containers, thumbnail placements, and viewport transitions. Understanding these differences involves examining the Shell Toolkit (St) layout managers, coordinate translations, and viewport clipping routines that govern each orientation.

Underlying Rendering Engine: Clutter and St

GNOME Shell builds its user interface using the Clutter toolkit and the Shell Toolkit (St). The workspace switcher, whether viewed inside the full-screen Activities Overview or as a floating on-screen display (OSD) popup, is composed of a hierarchy of Clutter.Actor instances.

In both orientations, workspaces are rendered as scaled-down clones or direct representations of the desktop stage. The primary difference lies in the St.BoxLayout or custom layout manager (Clutter.LayoutManager) used to sequence these workspace actors, which alters the distribution of translation vectors, sizing allocations, and clipping rectangles.

Horizontal Layout Rendering (Default in GNOME 40+)

The modern horizontal layout organizes workspaces sequentially along the X-axis.

  1. Coordinate Translations: In the horizontal model, navigation changes the horizontal translation property (translation_x) of the container actor (WorkspacesView). When a user swipes or switches desks, the active workspace slides along the X-axis, with neighboring workspaces rendered to the immediate left and right.
  2. Overview Geometry: Inside the Activities Overview, workspace previews are centered horizontally. The overview maintains a primary workspace in the center of the display while adjacent workspaces peak into the viewport from the screen edges. This requires GNOME Shell to compute preview scales dynamically based on monitor width, minus the margins consumed by the top bar and the Dash.
  3. Workspace Thumbnail Strip: Thumbnails are arranged in a horizontal row, positioned between the search entry and the main workspace view. The thumbnail container allocates fixed-aspect-ratio miniatures based on horizontal spacing rules, scrolling horizontally if the number of dynamic workspaces exceeds the monitor width.
  4. Input Mapping: 1:1 touchpad gestures calculate delta values directly along the X-axis, binding pointer or touch coordinates to the interpolation of the Clutter actor's X-position.

Vertical Layout Rendering (Legacy GNOME 3.38 and Extensions)

In the classic vertical layout, workspaces exist sequentially along the Y-axis.

  1. Coordinate Translations: Vertical workspace switchers manipulate the vertical translation property (translation_y) of the workspace container. Transitions occur strictly up and down.
  2. Overview Geometry: The active workspace occupies the majority of the screen without showing glimpses of the workspaces above or below it on the main stage. Instead, spatial awareness is maintained through a dedicated thumbnail rail pinned along the right edge of the screen.
  3. Workspace Thumbnail Rail: The thumbnail strip uses an St.BoxLayout with a vertical orientation (vertical: true). Thumbnails stack downward, scaling down in size when the number of workspaces increases to prevent the rail from exceeding the monitor’s vertical height bounds.
  4. Input Mapping: Mouse wheel scrolling and vertical gestures drive the Y-axis interpolation. The switcher popup (WorkspaceSwitcherPopup) appears as a vertically aligned indicator on the right or center of the display, rendering workspace boxes stacked on top of one another.

Viewport Management and Performance

The choice between vertical and horizontal rendering affects how Mutter clips off-screen contents:

  • Horizontal Rendering: Requires broader viewport allocation to render the visible segments of adjacent workspaces on either side of the active desktop. Clutter maintains these neighboring actors in a drawn state to ensure smooth real-time gesture scrubbing, increasing the overall texture memory footprint during transition animations.
  • Vertical Rendering: Typically isolates the rendering to the active workspace on the main canvas, offloading adjacent previews solely to small thumbnail clones in the side rail. This minimizes stage redraw overhead because off-screen workspaces remain culled until an explicit switch signal transitions the Y-coordinate.
