How GNOME Software Manages Automatic Flatpak Updates

GNOME Software streamlines application maintenance by automatically handling Flatpak updates in the background. It achieves this by coordinating its background service with the libflatpak API, monitoring network conditions, and taking advantage of Flatpak's sandboxed, transaction-based architecture. This article explains the underlying mechanism GNOME Software uses to check for, download, and apply these updates seamlessly without requiring system restarts or interrupting active user workflows.

Background Scheduling and Detection

When automatic updates are enabled, GNOME Software runs as a persistent background process launched during the user session. It periodically queries remote Flatpak repositories (such as Flathub) for metadata changes using libflatpak. Instead of polling continuously, the background service relies on scheduled internal timers—typically triggering checks once every day or upon system startup.

Network State Verification

Before initiating any download, GNOME Software checks the system's network status via NetworkManager and GLib networking APIs. If the connection is marked as metered (such as a mobile hotspot) or if data-saver modes are enabled, GNOME Software postpones the automatic update. This ensures large runtime downloads and application assets do not consume bandwidth unexpectedly.

Silent Downloading and Staging

Once an unmetered connection is confirmed, GNOME Software silently downloads the updated OSTree commits for the target Flatpak applications and runtimes. Because Flatpak applications are decoupled from the host operating system's base packages, these downloads are staged directly into the local Flatpak storage directory (either system-wide at /var/lib/flatpak or per-user at ~/.local/share/flatpak). This process requires no root authentication for user-level installations, and system-level installations use Polkit policies configured to allow silent background staging.

Safe Application Deployment

Flatpak relies on OSTree, an immutable, content-addressed object store similar to Git. Because files are addressed by their checksums, the new version of an application can be written to disk while an older version is actively running. GNOME Software deploys the new OSTree commit and updates the application's reference point in the background.

Active application processes remain unaffected because their open file descriptors still point to the previous version's runtime environment. The next time the user closes and relaunches the application, the system launches the newly deployed version.

Configuration via GSettings

This automated lifecycle is governed by the GNOME desktop configuration system. The feature is controlled by the download-updates key located within the org.gnome.software GSettings schema. When this toggle is turned off in the GNOME Software preferences, the background process restricts itself to downloading metadata only, leaving the download and deployment phases to manual user interaction.
