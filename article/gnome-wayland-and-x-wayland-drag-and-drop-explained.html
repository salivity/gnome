GNOME Wayland and XWayland Drag and Drop Explained

GNOME manages drag-and-drop operations between native Wayland applications and legacy XWayland clients through a translation layer integrated into its compositor and window manager, Mutter. Because Wayland and the X Window System rely on completely different inter-process communication mechanisms for data exchange, Mutter acts as an active proxy. It translates native Wayland data transfer protocols into the X11 XDnD protocol and vice versa, allowing users to drag files, text, and other payloads between legacy and modern applications seamlessly.

The Protocol Divide

Native Wayland and X11 implement clipboard and drag-and-drop (DnD) systems using fundamentally different architectures:

  • Wayland Native: Relies on the wl_data_device, wl_data_source, and wl_data_offer interfaces. The compositor directly mediates the transfer using standard UNIX file descriptors (pipes) negotiated via MIME types.
  • X11 / XWayland: Relies on the standard X Drag-and-Drop protocol (XDnD). Clients exchange X11 ClientMessage events (XdndEnter, XdndPosition, XdndStatus, XdndDrop) and transfer actual data payloads via X11 properties and atom-based selection mechanisms.

Because clients under XWayland cannot directly communicate with the Wayland compositor’s internal data-device architecture, Mutter bridges the two environments.

Dragging from a Wayland Native App to XWayland

When a user initiates a drag action within a native Wayland client and moves the pointer into an XWayland-managed window:

  1. Offer Registration: The Wayland source client advertises the offered MIME types using wl_data_source.offer to Mutter.
  2. Boundary Crossing: When Mutter detects the pointer crossing into an XWayland surface, it initializes an internal proxy.
  3. XDnD Emulation: Mutter translates the Wayland MIME offers into corresponding X11 atoms (for example, mapping text/plain;charset=utf-8 to UTF8_STRING). Mutter then generates synthetic X11 XDnD events, sending XdndEnter and XdndPosition events to the target XWayland window on behalf of a virtual X11 drag source.
  4. The Drop Action: Upon release, Mutter sends an XdndDrop event to the target X11 window.
  5. Payload Streaming: The XWayland application issues a standard XConvertSelection request for the data. Mutter intercepts this request, opens a UNIX pipe to the native Wayland source via wl_data_source.send, reads the stream, and transfers the data into the requested X11 window property.

Dragging from XWayland to a Wayland Native App

When dragging begins inside an XWayland window and targets a native Wayland window:

  1. XDnD Interception: The XWayland client emits an XdndEnter event containing a list of supported X11 atoms. Mutter intercepts these messages before they reach the root window.
  2. MIME Synthesis: Mutter creates a synthetic Wayland wl_data_source that advertises the corresponding MIME types equivalent to the detected X11 atoms.
  3. Wayland Negotiation: As the pointer enters the native Wayland window, Mutter sends wl_data_device.enter and wl_data_device.data_offer events to the native client, presenting the synthesized MIME options.
  4. The Drop Action: When the user releases the input button, the native Wayland client accepts an offered MIME type and passes a writable file descriptor back to Mutter via wl_data_offer.receive.
  5. Selection Request and Pipe Transfer: Mutter requests the selection from the XWayland source application via the X11 mechanism (XdndSelection). As the XWayland application writes the data to the X selection, Mutter reads the payload and writes it directly into the file descriptor supplied by the native Wayland target.

Format and Atom Mapping

A critical function of Mutter during this bridging process is data type conversion. Wayland relies strictly on Internet media types (MIME types, such as text/uri-list or image/png), whereas X11 applications often rely on legacy target atoms (such as STRING, TEXT, UTF8_STRING, or image/x-win-bitmap). Mutter maintains a bidirectional lookup table that maps standard MIME formats to their historical X11 equivalents, ensuring that file managers, web browsers, and text editors correctly interpret the data payload regardless of the display server protocol they target.
