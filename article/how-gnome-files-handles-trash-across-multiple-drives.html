How GNOME Files Handles Trash Across Multiple Drives

GNOME Files (also known as Nautilus) provides trash management and restoration across multiple physical drives by adhering to the FreeDesktop.org (XDG) Trash Specification. Instead of transferring deleted files across different storage devices to a single central directory—which would cause severe performance bottlenecks and cross-filesystem copy operations—GNOME Files delegates trash storage directly to the drive where the files reside. It creates isolated, per-volume trash directories, merges these locations into a single unified view in the graphical interface, and leverages metadata files to execute instant, accurate restorations.

Per-Volume Trash Directories

Moving a file between distinct physical drives or filesystem partitions requires copying data byte-for-byte and deleting the original, which violates the expected near-instantaneous behavior of moving a file to the trash. To prevent this, GNOME Files creates a localized trash folder on the root of each secondary physical drive or partition.

When a file is deleted on a non-root drive, GNOME Files attempts to locate or create one of the following directories at the top-level mount point:

  1. Administrator-Created Directory (.Trash/$UID): If a top-level .Trash directory exists with appropriate permissions (sticky bit set), GNOME Files creates a subfolder named after the user’s numerical User ID (e.g., .Trash/1000).
  2. User-Owned Fallback Directory (.Trash-$UID): If the shared .Trash folder does not exist or cannot be accessed, GNOME Files automatically creates a directory named .Trash-$UID (such as .Trash-1000) directly at the mount point root.

Files deleted from the main system drive are stored in the user's home directory under ~/.local/share/Trash. Files deleted on external or secondary drives remain physically located on those specific storage devices inside their respective .Trash-$UID directories.

Directory Structure and Metadata Storage

Every trash container—whether the local home trash or an external drive trash—maintains an identical dual-folder hierarchy:

  • files/: Contains the raw, renamed or original data payload.
  • info/: Contains a companion metadata file with a .trashinfo extension for every corresponding item in the files/ directory.

The .trashinfo file records two critical pieces of data using a key-value format:

  • Path: The absolute path of the file prior to deletion, indicating its exact original location on that filesystem.
  • DeletionDate: An ISO 8601 timestamp recording when the item was moved to the trash.

Because the path is relative to the mount point or fully qualified within the local filesystem, the item never leaves the physical storage boundaries of that specific disk.

The Unified Trash Interface

In GNOME Files, navigating to the "Trash" sidebar entry opens a virtual URI (trash:///). The file manager scans the primary trash path in ~/.local/share/Trash and concurrently polls every currently mounted volume for valid trash directories belonging to the current user.

GNOME Files aggregates the contents of these disparate physical locations into a single, unified view. Users interact with deleted files as if they were stored together, regardless of how many external hard drives, USB flash drives, or secondary SSDs are attached to the system. If an external drive is safely unmounted or removed, its deleted contents simply disappear from the trash:/// interface until the drive is reconnected.

Cross-Drive Restoration Mechanics

When a user initiates the "Restore" action on an item in the trash, GNOME Files executes the following sequence:

  1. It reads the corresponding .trashinfo file from the specific drive's info/ directory.
  2. It extracts the original location recorded under the Path parameter.
  3. If the destination parent directory was deleted, GNOME Files recreates the missing folder hierarchy on that drive.
  4. It issues an atomic move operation (rename syscall), moving the payload from .Trash-$UID/files/ directly back to its original path on the same drive.
  5. It removes the .trashinfo metadata entry.

Because the entire operation occurs within the same physical filesystem boundary, restoration is virtually instantaneous, avoids data transfer over system buses, and ensures that file permissions and ownership attributes remain intact.
