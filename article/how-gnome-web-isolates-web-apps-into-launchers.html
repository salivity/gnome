How GNOME Web Isolates Web Apps into Launchers

GNOME Web (Epiphany) isolates web applications by treating each site as an independent entity with its own storage, process context, and desktop integration files. Rather than running websites inside shared browser tabs, GNOME Web creates a dedicated profile directory, provisions a custom .desktop launcher, and invokes a streamlined WebKitGTK instance in application mode, ensuring that each web app operates in an isolated environment detached from standard browsing data.

Dedicated Application Profiles and Data Separation

When you use the "Install Site as Web Application" feature in GNOME Web, the browser generates an isolated profile directory specifically for that domain. On traditional installations, these are stored in ~/.local/share/epiphany/web-apps/, while Flatpak installations store them in the user's Epiphany sandbox directory under ~/.var/app/org.gnome.Epiphany/data/epiphany/web-apps/.

Each directory is assigned a unique identifier (often a hash or domain-based name) and contains its own:

  • Cookies and Session Storage: Web apps cannot read or modify cookies used in your primary browser or in other web applications.
  • Cache and Local Storage: IndexedDB, Web SQL, and cache files reside strictly within that app's profile directory.
  • Credentials: Saved passwords and authentication tokens are kept isolated, preventing cross-site leakage between applications.

Independent .desktop Entry Creation

To integrate seamlessly into the GNOME Shell, the browser writes a standard FreeDesktop .desktop entry to ~/.local/share/applications/.

This file defines metadata such as the app’s name, icon (fetched automatically from the website's favicon or web app manifest), and its execution command. The execution line specifies the application mode flag and passes the explicit path to the unique profile:

Exec=epiphany --application-mode --profile="/path/to/profile" "https://example.com"

Because it possesses its own .desktop file, the web application registers a unique application ID (app-id). This enables GNOME Shell's window manager (Mutter) to manage, dock, search, and switch between web apps in the dash and the Alt+Tab switcher as if they were native GTK applications.

UI and Window Shell Containment

Launching via --application-mode strips away standard web browser UI elements. The navigation bar, back/forward buttons, tab strip, extensions, and universal settings menus are hidden.

The window is rendered as a clean, single-purpose application frame that relies purely on web-internal navigation or custom header bars generated by the web app's manifest, further preventing accidental cross-domain browsing.

Process and WebKitGTK Runtime Isolation

At runtime, GNOME Web spawns a new WebKitGTK process hierarchy bound specifically to the application's profile directory. Modern WebKitGTK architecture enforces process separation between the UI process and the underlying WebProcess executing JavaScript and network requests.

Because the process is bound only to the specific profile directory, any security event, crash, or memory overflow inside that web application remains constrained to that instance. It will not disrupt the main browser session or any other running web apps.

Flatpak Sandboxing and Portal Usage

When GNOME Web runs as a Flatpak, it uses XDG Desktop Portals to create web launchers on the host system without compromising its own sandbox.

The browser uses the Dynamic Launcher portal (org.freedesktop.portal.DynamicLauncher) to request the host system to install the .desktop file and corresponding icon. When launched from the host application grid, the launcher invokes the Flatpak runtime with parameters telling the sandboxed Epiphany instance to launch the specific profile, keeping host-level and application-level permissions strictly controlled.
