How GNOME Integrates with systemd-oomd

Modern Linux desktops historically suffered from catastrophic system lockups and unresponsive interfaces when physical memory and swap were exhausted. This article explains how the GNOME desktop environment integrates with systemd-oomd using cgroups v2 and Memory Pressure Stall Information (PSI) to proactively terminate misbehaving applications before system lockup occurs, maintaining user interface responsiveness during extreme memory pressure.

Traditionally, the Linux kernel handled out-of-memory situations via its in-kernel OOM killer. The kernel killer typically intervenes only when memory allocation completely fails, often preceded by severe disk thrashing as the system frantically swaps pages. This thrashing freezes the desktop environment and input devices for minutes at a time. To prevent these freezes, user-space out-of-memory daemons were developed, with systemd-oomd becoming the standard implementation across several major distributions like Fedora and Ubuntu.

GNOME's integration with systemd-oomd relies fundamentally on control groups version 2 (cgroups v2) and the systemd user session. When a user logs into GNOME, the session manager and application launchers do not simply execute programs as unmanaged child processes. Instead, GNOME leverages systemd transient scopes and services to categorize every process into a hierarchical structure:

  • System and Session Infrastructure: Core components like gnome-shell, mutter, and essential session services are isolated within session.slice.
  • User Applications: User-facing graphical applications launched through GNOME Shell or the application menu are assigned their own transient scopes within app.slice (for example, app-gnome-firefox-12345.scope).
  • Background Tasks: Auxiliary services and background workers are placed into background.slice.

This isolation allows systemd-oomd to treat applications as discrete resource units rather than dealing with isolated, disparate PIDs.

To determine when to intervene, systemd-oomd monitors Linux Pressure Stall Information (PSI). PSI measures the percentage of time that tasks are delayed waiting for memory resources, serving as an early-warning detection system long before total allocation failure. Administrators and distributions define pressure thresholds within systemd slice configuration files.

When memory pressure exceeds configured thresholds for a sustained period, systemd-oomd triggers an intervention. Rather than indiscriminately killing processes or killing the desktop compositor, it inspects the cgroup hierarchy. Because GNOME separates applications into distinct units within app.slice, systemd-oomd targets the specific cgroup consuming the most memory or generating the highest pressure stall within that slice.

The daemon terminates the offending cgroup using a SIGKILL signal. Because gnome-shell resides in an entirely separate slice (session.slice) with lower priority for termination, the desktop interface remains interactive throughout the incident. Once an application is terminated, memory pressure drops immediately, and GNOME can gracefully continue running without requiring a hard system reboot.
